01
Premisewhy give a chip a mind

The statusline has spent forty years displaying state. What if one started having opinions?

A statusline is the most honest piece of UI a developer owns. It earns its row of pixels by surfacing the things you actually need to glance at — branch, dirty tree, model, context percentage, ssh tunnel up or down — and it gets out of the way. Every chip is an if/else away from a number, and the whole line is auditable in a thousand-line bash script.

The premise here was small: what happens if one of those chips stops being deterministic and starts having a small, local opinion? Not an LLM in the render path — that would be slow and stupid — but an LLM running quietly in the background, watching the same signals the deterministic chips watch, and choosing one thing worth saying.

Two chips were built. One — a greeter — would speak once at session start, synthesizing the last session's wrap-up with the current directory into one sentence. The other — an adaptive slot — would refresh every five minutes on a launchd timer, picking one actionable insight from a handful of local signals.

The unit cost One haiku call per session is one tenth of one cent. One qwen2.5 call every five minutes is electricity. The whole experiment cost less than the coffee that started it.

03
Pipelinethe moving parts

The render is fast because the thinking happens elsewhere.

The trick to putting an LLM in a statusline is not putting it in the statusline. The render path stays a pure bash script that reads files from /tmp; everything intelligent runs out-of-band, on a schedule that has nothing to do with the user's next keystroke.

render path · every turn · ~100ms ──────────────────────────────── statusline-command.sh reads /tmp files, renders chips, forks stale refreshes ▲ │ ┌───────────────────────────────────┼───────────────────────────────────┐ │ │ │ ▼ ▼ ▼ SessionStart hook opportunistic fork (45min) opportunistic fork (10min) session-start-greeter.sh adaptive-slot-haiku.sh triage-poller.sh (forks, returns in 36ms) (forks, lock prevents dups) (forks, ~2s ssh round trip) │ │ │ ▼ ▼ ▼ claude haiku claude haiku ssh → Mac Mini session last_ended + cross-signal signals + Asana + Sentry + cron MEMORY.md top + cwd anti-duplication rules (tokens live remotely) │ │ │ ▼ ▼ ▼ /tmp/.claude-greeter-${sid} /tmp/.claude-slot /tmp/.claude-triage.json fades after 5 min fresh for 75 min fresh for 15 min

Two design choices made this cheap. The first: fork the slow work. The SessionStart hook returns in 36 milliseconds; the haiku call runs in a detached subshell and writes its result whenever it arrives. The session doesn't wait for the model. The greeter is simply missing for the first few turns, then appears.

The second: file-as-state. The render loop never makes a network call. It reads a file. The file may be empty (the LLM chose silence), stale (the scheduler stopped), or missing (the hook never fired). All three cases collapse to "show no chip" — a single line of bash.

# the slot chip's render block — 8 lines, all conditional, never blocks slot_info="" slot_file="/tmp/.claude-slot" if [ -r "$slot_file" ]; then s_mtime=$(stat -c %Y "$slot_file" 2>/dev/null) [ -z "$s_mtime" ] && s_mtime=$(stat -f %m "$slot_file" 2>/dev/null) if [ $((now - s_mtime)) -lt 600 ]; then slot_text=$(head -c 60 "$slot_file" | tr -d '\n') [ -n "$slot_text" ] && slot_info=" 💡 $slot_text" fi fi
Bash 3.2 trap macOS still ships bash 3.2 — Apple stopped at the last GPLv2 release. Launchd uses /bin/bash, so all the modern conveniences (nested $() with quoted args, empty-pattern case branches) silently fail. The script's heredoc had to be rewritten with single-quoted EOF + sed substitution. Every script that crosses the launchd boundary deserves a 3.2 compatibility pass.
The render path stays dumb. The thinking happens elsewhere, on a schedule, in a file.
Design rule · written down after the second debugging session
04
The mistakewhat the AI kept saying

The slot picked the loudest signal — which was already on screen.

The adaptive slot was prompted with six signals: stale context count, Mac Mini reachability, dirty files in two projects, unpushed commits, memories added today, and time of day. Its job was to pick one and turn it into a chip text of thirty characters or fewer.

What it picked, almost every time, was the stale context count. The number was small and integer, the verb was obvious — "import" — and the chip wrote itself: import 1 stale contexts. Useful, technically actionable, easy to evaluate.

The problem was that the chip immediately to its right, ⟳ 1, was the deterministic freshness chip. It already said the same thing. Less verbosely, in two characters and a number, in a color the eye reads in eighty milliseconds. The slot was rephrasing what was already on the line.

mini 💡 import 1 stale contexts ⟳ 1 "work"
redundant chip redundant chip · same info, twice

The lesson is brutal and small. An AI-generated chip has to surface what the deterministic chips cannot — cross-signal synthesis, time-of-day patterns, the absence of an event, the soft judgment that a branch has been idle long enough that you may have forgotten about it. If the model can only restate one number that's already on screen, the chip is noise, not signal.

So the slot was removed. Launchd unloaded, plist deleted, the chip's render block stripped from the script, the /tmp/.claude-slot file cleaned. The script that wrote it still lives on disk — not running — in case a smarter prompt ever wants the territory.

What a useful slot would have said "helixa idle 9d · still relevant?" — pulled from MEMORY.md, cross-referenced with last commit on the helixa branch, surfacing an absence. That's the kind of judgment a deterministic chip can't produce. The current prompt didn't ask for it.
05
What survivedthe one sentence worth keeping

The greeter said one thing, and meant it.

On a fresh session in the memory project, the greeter rendered:

// SessionStart greeter · Claude haiku · ~$0.001 per call memory MCP ready · helixa/customer360 next?

One sentence. It picked up two facts from inputs that the deterministic chips never see: that the current directory was the memory MCP server's source tree, and that customer360 appeared near the top of MEMORY.md — meaning it was recent active work. It bridged them with a question mark — soft suggestion, not an instruction.

No deterministic chip can produce that line. No if/else over six signals composes "helixa/customer360" as a phrase. The synthesis is the entire value. That's the only thing the greeter has to do, and it does it for a fraction of a cent.

The other lesson was about fading. The greeter holds the chip for five minutes after session start, then disappears. Its job is orientation, not residence. A chip that survives forever stops earning its row of pixels.

Why haiku, not local A 14B local model could have written that sentence, technically. But the synthesis quality of haiku on small prompts is meaningfully better, and the per-session cost — one tenth of one cent — is rounding error. Use the smarter model where the output is precious and runs once. Use local where the output is throwaway and runs constantly.
06
Resurrectionthe chip came back smarter

The slot returned — different model, different scheduler, different rules.

Killing the slot was correct. Leaving it killed wasn't. The territory the slot occupied — one chip slot reserved for cross-signal AI insight — was still valuable; only the V1 implementation was wrong. So a V2 was designed with three constraints carved in at the prompt level.

Constraint one: the prompt now explicitly enumerates which signals the user already sees deterministically and forbids any rephrase. The chip's only job is what's not on screen — idle days, time-of-day patterns, soft suggestions. Constraint two: synthesis quality matters more than refresh frequency. Use Claude haiku, not a 14B local model. The output is precious; spend on it. Constraint three: refresh slowly enough to stay in subscription budget. Every 45 minutes, not every 5.

That third constraint surfaced a problem. Launchd was the obvious scheduler for "every 45 minutes," but launchd processes can't read the macOS Keychain entry holding Claude's OAuth credentials. claude -p from a launchd-spawned bash returns Not logged in. The greeter dodges this because Claude Code itself invokes the SessionStart hook, so the greeter inherits auth. The slot, refreshing on a schedule independent of any session, had no parent to inherit from.

# the diagnostic that revealed it — five lines of bash, twenty seconds of confusion $ env -i HOME=$HOME PATH="/opt/homebrew/bin:/usr/bin:/bin" bash -c 'claude -p "say ok"' Not logged in · Please run /login $ claude auth status { "loggedIn": true, "authMethod": "claude.ai" } # auth IS present, just unreachable

The fix was a pattern, not a tool. Instead of launchd, the slot refreshes opportunistically from inside the statusline itself. The statusline runs every turn — inside Claude Code's auth context. It checks whether the slot file is older than 45 minutes; if so, it forks a subshell that calls claude -p, which inherits the parent's auth. A lock file prevents duplicate forks during the ~20-second LLM call. The render path stays under 100ms because forking is microseconds.

The byproduct: refresh cadence now follows your activity. When you're actively working, the slot refreshes every 45 minutes. When you're idle, it stops refreshing — which is fine, because nobody is looking at it. The scheduler became the user, in the sense Unix has always intended.

Auth inheritance, the pattern Any process Claude Code invokes — hooks, statusline command, MCP servers — gets credentials for free. Any process scheduled outside Claude Code's tree — launchd, system cron, login items — does not. Design your background refreshes to fire through Claude Code's tree, not parallel to it.

07
Cross‑machinetokens stayed home

The triage chip pulls state from a machine the local Mac has never seen credentials for.

The triage chip aggregates three sources of "things waiting on you": open Asana tasks in the triage queue, unresolved Sentry issues in the last 24 hours, and Mac Mini cron jobs in an error state. The naive approach is to put all three API tokens on the local Mac and call out. The right approach is to recognize that all three tokens already exist somewhere else — on Mac Mini, where the existing cron-based triager runs them every few minutes — and to never copy them.

The poller is fifty lines of bash. It opens an ssh connection to a remote worker box via a Host alias and ed25519 key, ships a remote bash payload that reads its own environment for ASANA_ACCESS_TOKEN and SENTRY_AUTH, runs three curls in parallel, aggregates the counts into a single line of JSON, and writes it to stdout. The local Mac sees only the JSON. Tokens never crossed the network as values, only as references inside a remote process's env. SSH key auth means no password ever lives in any script.

# the architectural choice in one ssh invocation ssh -o BatchMode=yes worker bash -s '<<REMOTE' # this entire block executes on the remote worker, with its env # `worker` is a ~/.ssh/config Host alias bound to an ed25519 key ASANA_COUNT=$(curl -s -H "Authorization: Bearer $ASANA_ACCESS_TOKEN" ...) SENTRY_COUNT=$(curl -s -H "Authorization: Bearer $SENTRY_AUTH" ...) CRON_ERR_COUNT=$(jq '.jobs | map(select(...)) | length' ~/.openclaw/cron/jobs.json) printf '{"asana":%d,"sentry":%d,"cron_errs":%d,"total":%d}' ... REMOTE

The chip color-grades by total backlog: green when clear, yellow when 1 to 3 items, terra cotta at 4 or more. When Mac Mini is unreachable — VPN dropped, machine asleep — the JSON returns reachable: false and the chip hides honestly rather than going stale. The breakdown after the total shows which source contributed: 3a 2s 1c means three Asana, two Sentry, one cron error. Six characters of forensics.

The blast-radius argument Rotating an Asana PAT or a Sentry token now requires changing one machine, not two. Same security-blast-radius as the existing cron-based triager. The triage chip added zero new attack surface to the local Mac, because the local Mac has nothing new to attack.
08
Two mindswhen the chip is right and wrong

The slot once said "memory idle 101 days" — and was completely correct, and completely wrong.

The slot's prompt included a signal called hours since last memory write, computed by querying SELECT MAX(inserted_at) FROM memories against the Memory MCP server's PostgreSQL database. The query returned a timestamp from 101 days ago. The slot duly synthesized: memory idle 101d · sync?

And the chip was, strictly, right. The MCP server's database has not seen a new row in 101 days — because the user stopped writing memories through the MCP protocol months ago. But the user is also writing memory files constantly, just to a different system: the file-based auto-memory layer at ~/.claude/projects/.../memory/*.md, which had been updated thirty seconds before the chip rendered.

Two memory systems. The chip looked at one. The user thinks of the other when they read the word "memory." So the chip was honest but unaligned with the user's mental model — which is the same as wrong, in UI.

memory_dev.memories: last write 101d ago → memory is idle
auto-memory MEMORY.md: last write 30s ago → memory is very much alive

The fix was a one-line change in the signal-gathering code: replace the psql query with a find -mtime against the auto-memory directory. The slot now says, accurately and usefully, helixa idle 44h · still on? — picking the synthesis the user can actually act on.

The lesson is structural. An AI chip can read a perfectly truthful signal and still be wrong, because "truthful" is a property of the world and "useful" is a property of the reader. When the chip and the reader disagree on which world the chip is describing, the reader is always right.

The user's first reaction A two-word question typed into the terminal: memory idle? — which was enough to find and fix the bug in one round. The chip had become a thing worth questioning. That's its own win.

Net: twelve chips ship. Two are AI-driven, two are remote-sourced, eight are deterministic. One chip was killed once and resurrected smarter. Three design rules got written down. Six hours from premise to production, mostly spent learning what AI shouldn't say in UI you stare at twelve thousand times a day.

The rule, posted AI status chips must surface what the deterministic chips cannot. Cross-signal synthesis, time-of-day patterns, the absence of an event, or non-numeric judgment. Anything else is noise wearing a hat.
